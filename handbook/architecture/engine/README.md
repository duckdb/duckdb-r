# The engine

The DuckDB engine embedded in `src/duckdb/`:
which upstream commit is embedded,
how that version reaches R,
and how this package's build of the engine differs from a stock build.
The engine itself — SQL dialect, storage format, execution, tuning —
is documented by DuckDB at
[duckdb.org/docs](https://duckdb.org/docs/)
and in [duckdb/duckdb](https://github.com/duckdb/duckdb),
and is not repeated here.
How the embedded copy is kept current
is [`operations/vendoring/`](/handbook/operations/vendoring/).

## Which commit is embedded

`src/duckdb/` is a copy of the upstream sources,
regenerated by [`scripts/rconfigure.py`](/scripts/rconfigure.py)
from a DuckDB checkout,
one upstream commit per vendor commit.
Two identifiers travel with the copy,
both defined in
`src/duckdb/src/function/table/version/pragma_version.cpp`:
`DUCKDB_VERSION`, the release string, such as `v1.5.5`,
and `DUCKDB_SOURCE_ID`, the abbreviated upstream commit.
`PRAGMA version` returns both,
as the `library_version` and `source_id` columns.

`DUCKDB_SOURCE_ID` is the identity the fast path checks
before it links a prebuilt `libduckdb`
([`build/fast-paths/`](/handbook/build/fast-paths/)).

## The version R reports

`rconfigure.py` reads `DUCKDB_VERSION` at vendor time,
strips the leading `v`,
and writes [`R/version.R`](/R/version.R),
which holds `duckdb_version` and `get_duckdb_version()`.
The version is therefore a compile-time constant on the R side:
`dbGetInfo()` reports it as `driver.version` and `client.version`
for a driver,
and as `db.version` for a connection,
without opening a database.
`R/version.R` is generated —
a correction belongs in `rconfigure.py`, not in the file.

The package version in `DESCRIPTION` is a different number.
It carries the engine version plus the package's own counters;
[`operations/releases/versioning/`](/handbook/operations/releases/versioning/)
owns it.

## How this build differs from a stock build

The engine is compiled as part of the R package,
as C++17 (`CXX_STD = CXX17`),
with the flags in `PKG_CPPFLAGS` in
[`src/Makevars.in`](/src/Makevars.in)
plus the include and extension list that `rconfigure.py` splices in.
`src/Makevars` and `src/Makevars.win` are the generated results;
[`build/source-build/`](/handbook/build/source-build/) owns those files.
Beyond the flags, the vendored sources themselves carry R-specific
modifications from the patch stack under `patch/`,
which is
[`operations/vendoring/pipeline/`](/handbook/operations/vendoring/pipeline/)'s
topic.

| Flag | Effect |
|---|---|
| `-DDUCKDB_DISABLE_PRINT` | Compiles out every direct `fprintf()` to stdout and stderr in `Printer`, so the engine cannot write to the R console behind R's back. `IsTerminal()` and `TerminalWidth()` throw instead of querying a terminal. |
| `-DDUCKDB_R_BUILD` | Marks the build as the R one. Its only use in the vendored tree replaces the `atomic` next pointer in `SegmentNode` with a plain pointer. |
| `-DBROTLI_ENCODER_CLEANUP_ON_OOM` | Makes the bundled Brotli encoder clean up and return on allocation failure instead of calling `exit()`, which an R package must not do. |
| `-DDUCKDB_EXTENSION_AUTOLOAD_DEFAULT` | Flips the default of the `autoload_known_extensions` setting to `true`. `autoinstall_known_extensions` is not flipped and stays `false`. |
| `-DDUCKDB_BUILD_LIBRARY` | Marks `DUCKDB_API` symbols as exported rather than imported on Windows. |
| `-DDUCKDB_EXTENSION_PARQUET_LINKED`, `-DDUCKDB_EXTENSION_CORE_FUNCTIONS_LINKED` | The linked extension set, below. |
| `-DDUCKDB_RSTRTMGR=0\|1` | Written by `configure` / `configure.win`. `0` on R < 4.2 on Windows, where `librstrtmgr.a` is not available; a patch makes the Restart Manager code conditional on it. `1` everywhere else. |
| `-DDUCKDB_PLATFORM_RTOOLS=1` | Windows only. Gives the platform string the `_mingw` postfix, so extension downloads resolve to the builds Rtools can load. |

`rconfigure.py` also honors a few environment variables set at vendor
time: `TREAT_WARNINGS_AS_ERRORS` appends `-Werror`,
`DUCKDB_DEBUG_MOVE` appends `-DDUCKDB_DEBUG_MOVE`,
and `DUCKDB_R_LINENR` and `DUCKDB_BUILD_UNITY` change how the sources
are amalgamated.
Neither `-Werror` nor `-DDUCKDB_DEBUG_MOVE` is in force for the shipped
build — the committed `src/Makevars` carries neither flag.

## The linked extension set

`rconfigure.py` starts from `parquet` and `core_functions`
and appends whatever `DUCKDB_R_EXTENSIONS` names,
turning each into `-DDUCKDB_EXTENSION_<NAME>_LINKED`.
The committed `src/Makevars` therefore links `parquet` and
`core_functions` and nothing else;
the `-DDUCKDB_EXTENSION_*_LINKED` defines in that file are the
authoritative list.

The set is fixed when the package is vendored, not when it is installed:
`DUCKDB_R_EXTENSIONS` only has an effect on a run of `rconfigure.py`
(the knob is
[`build/configuration/`](/handbook/build/configuration/)'s),
and what a user can load at runtime is
[`usage/extensions/`](/handbook/usage/extensions/)'s.
A release `libduckdb` links a wider set and defaults differently,
which is why engine configuration is never verified on the fast path
([`build/fast-paths/`](/handbook/build/fast-paths/)).

## The allocator

The engine uses its standard allocator.
`DUCKDB_ENABLE_JEMALLOC` is never defined,
and `rconfigure.py` drops the `third_party/jemalloc` tree
from the generated source list.
Upstream began emitting that tree into the R package's sources
in [duckdb/duckdb#22811](https://github.com/duckdb/duckdb/pull/22811),
which broke the build twice over:
`jemalloc_cpp.cpp` requires `DUCKDB_OVERRIDE_NEW_DELETE`,
and jemalloc's constructor references `duckdb_malloc_ncpus()`,
which exists only under `DUCKDB_ENABLE_JEMALLOC`.
Excluding the tree restored the previous behavior.

Whether to enable jemalloc deliberately is open
([#2365](https://github.com/duckdb/duckdb-r/issues/2365)).
Upstream reports it as available on Linux and macOS but not yet on
Windows, and suggests excluding `jemalloc_cpp.cpp` rather than taking
`DUCKDB_OVERRIDE_NEW_DELETE`;
what is missing is a benchmark that would show what the R package gains.
Until that exists, the exclusion stands.

## Warnings from the vendored tree

Compiling the vendored tree — well over a thousand C++ source files —
raises warnings that this package does not silence.
`g++` with `-std=gnu++17`, for instance, reports every
`TryCastWithOverflowCheck()` overload in `numeric_cast.hpp` as
`defined but not used`
([#1829](https://github.com/duckdb/duckdb-r/issues/1829)).
The warnings are noise, not failures:
the shipped build does not set `-Werror`.

They are also not suppressed.
The no-suppression policy, and the rule that a warning in vendored code
is fixed by a patch under `patch/` or upstream rather than by a
`-Wno-` flag or a `#pragma`, is
[`architecture/glue/`](/handbook/architecture/glue/)'s.
