# The R layer

Everything under `R/`:
where a method lives,
which files are generated and by what,
how the package refers to itself without writing its own name,
the S4 classes it defines,
and how methods for optional packages are registered at load time.
The C++ half of the same interface is
[`architecture/glue/`](/handbook/architecture/glue/README.md).

## One file per method

`R/` is flat,
and every S4 method the package defines lives in a file of its own,
named `<generic>__<signature>.R`:
`dbBegin__duckdb_connection.R`,
`dbWriteTable__duckdb_connection_character_data.frame.R`.
The naming convention is therefore the index:
the `__` files are where the S4 methods are,
and there is no `setMethod()` call anywhere else in `R/`.

Each defines a plain function named after the file
and then registers it:

```r
dbBegin__duckdb_connection <- function(conn, ...) {
  dbExecute(conn, SQL("BEGIN TRANSACTION"))
  invisible(TRUE)
}

setMethod("dbBegin", "duckdb_connection", dbBegin__duckdb_connection)
```

A file may hold more than one `setMethod()` call
when the extra calls belong to the same pairing:
several signatures of one generic
(`dbQuoteIdentifier__duckdb_connection.R` registers several),
or a generic and its inseparable companion
(`dbBind` with `dbBindArrow`,
`dbFetchArrow` with `dbFetchArrowChunk`).
What never happens is two unrelated methods sharing a file.

The roxygen follows the same shape.
A method block carries `@rdname <class>-class` and `@usage NULL`,
so the methods document into their class's reference page
instead of producing a page each.

The convention covers methods, not the whole directory.
Constructors, helpers, and the interfaces that are not S4
are grouped by topic —
`Driver.R`, `Connection.R`, `Result.R`, `relational.R`, `storage.R` —
and S3 methods sit with the topic they serve:
the adbcdrivermanager methods in `Driver.R`,
the dplyr and dbplyr ones in `backend-dbplyr__duckdb_connection.R`,
`print`, `head`, `names`, and `as.data.frame` for relations
in `relational.R`.
Two files use the `__` name for S3 rather than S4 —
`print__duckdb_explain.R` and `backend-dbplyr__duckdb_connection.R` —
so the name marks "methods for one class", not "S4".

## Generated files

A few files under `R/` are generated and committed.
Each opens with a header saying so,
and a hand edit to any of them is a bug:
it passes review as ordinary R code,
then disappears the next time the generator runs,
taking whatever it fixed with it.
Change the generator or its input instead.

| File | Generated by | Runs |
|---|---|---|
| `R/cpp11.R` | `cpp11::cpp_register()` | after a change to the `[[cpp11::register]]` surface in `src/`, and inside `scripts/flavor.sh` |
| `R/rethrow-gen.R` | `scripts/rethrow.R` | on every R start in the repo, via `.Rprofile` |
| `R/version.R` | `scripts/rconfigure.py` | during vendoring |

`R/cpp11.R` holds the R side of the glue:
one `rapi_*()` function per registered entry point,
each a `.Call()` into the compiled symbol.
See [`architecture/glue/`](/handbook/architecture/glue/README.md)
for the C++ side it mirrors.

`scripts/rethrow.R` reads `R/cpp11.R`,
matches every `rapi_*` definition with a regular expression,
and writes one `rethrow_rapi_*()` wrapper per binding.
The wrapper runs the binding under `rlang::try_fetch()`
and hands any error to `rethrow_error_from_rapi()` in `R/rethrow.R`,
which re-raises it with `rlang::abort(call = )`
so the message points at the user's call
rather than at the binding.
R code calls `rethrow_rapi_*()`;
calling `rapi_*()` directly gives up the call context.
The generator also emits `rethrow_restore()`,
which rebinds every wrapper back to the bare binding —
the escape hatch used when rlang is absent (below).

`.Rprofile` sources `scripts/rethrow.R` on repo load,
so the file is regenerated as a side effect of starting R in a checkout.
It returns immediately when `CI` is set,
and when `R/rethrow-gen.R` is at least as new as `R/cpp11.R`,
so it costs nothing in the common case
and never rewrites in CI, where the committed file is what gets checked.
Regenerating by hand is a matter of touching `R/cpp11.R`
and restarting R, or sourcing `scripts/rethrow.R`.

`R/version.R` records the vendored DuckDB version
and belongs to the vendoring run that produced it —
[`operations/vendoring/pipeline/`](/handbook/operations/vendoring/pipeline/README.md).

## Never hard-code the package name

The package is published under several names —
`duckdb` on CRAN,
and `duckdb.dev`, `duckdb.1.5.dev`, `duckdb.1.4` and friends on
r-universe —
all built from the same sources,
with `scripts/flavor.sh` applying the rename
([`branches/flavors/`](/handbook/branches/flavors/README.md)).
Anything that writes `duckdb` literally
works on `main` and breaks on every other branch.

`R/package.R` is the seam:

| Helper | Returns |
|---|---|
| `get_package_name()` | the current package name, via `utils::packageName()` |
| `get_package_env()` | that package's namespace, via `asNamespace()` |
| `get_package_spec()`, `get_package_version()` | the namespace spec and version |
| `system_file_path(...)` | a path inside the installed package; also the seam tests stub instead of resolving a real install |

`simulate_duckdb()` exposes `get_package_name()` and `get_package_env()`
as `$pkg` and `$env`,
which is what makes
`@examplesIf simulate_duckdb()$env$examples_enabled()`
work under any flavor.

Use them anywhere the package refers to itself:

* `system.file(..., package = get_package_name())`,
  never the package name as a string literal;
* `get_package_env()$some_internal`,
  never a `:::` qualifier on our own name;
* in roxygen too —
  an inline chunk `` `r get_package_env()$CONSTANT` `` resolves under any
  name,
  while the same chunk written with a `:::` qualifier fails everywhere
  except `main`.

The roxygen case is worth calling out because it fails in a confusing way.
roxygen2 evaluates inline chunks in the package's own namespace,
so an unresolvable reference does not raise an error:
the chunk,
**and every other inline chunk in the same roxygen block**,
is emitted verbatim as `\verb{r ...}`.
A single hard-coded qualifier therefore silently de-evaluates its
neighbours —
a single qualified reference in `R/storage.R`
also took out the `lifecycle::badge()` chunk beside it.
The regenerated `.Rd` then differs from the committed one
and CI fails at the `roxygenize` step, before anything is compiled.

A few places have to spell the name out,
because R itself requires a literal there:
`Package:` in `DESCRIPTION`,
`@useDynLib` in `R/duckdb-package.R` and its `NAMESPACE` counterpart,
`library(duckdb)` in `tests/testthat.R`,
and `DUCKDB_PACKAGE_NAME` in `src/include/rapi.hpp`,
which is how the glue calls back into `rapi_error()` by name.
Those are rewritten by `scripts/flavor.patch`.
The `.Call()` symbols in `R/cpp11.R` carry the name too
(`_duckdb_rapi_connect`),
and are not patched but regenerated:
`scripts/flavor.sh` runs `cpp11::cpp_register()`
immediately after applying the patch.

A new literal that is neither routed through the seam
nor taught to the patch is a silent cross-package reference
in every flavor but the mainline one.
`scripts/flavor-package-name.R` scans for exactly that;
it is documented at
[`testing/guards/`](/handbook/testing/guards/README.md).

## The classes

The S4 classes, all exported:

| Class | Extends | Defined in |
|---|---|---|
| `duckdb_driver` | `DBIDriver` | `R/Connection.R` |
| `duckdb_connection` | `DBIConnection` | `R/Connection.R` |
| `duckdb_result` | `DBIResult` | `R/Result.R` |
| `duckdb_result_arrow` | `DBIResultArrow` | `R/Result.R` |
| `duckdb_explain` | `data.frame` | `R/print__duckdb_explain.R` |

The hierarchy is DBI's, one level deep:
each class extends the DBI virtual class it implements,
and only `duckdb_connection` refers to another of ours,
holding its `duckdb_driver` in a slot.

Handles into the engine are external pointers —
`database_ref` on the driver,
`conn_ref` on the connection,
`query_result` on the result.
Mutable per-result state does not live in slots at all:
an S4 object is copied on modification,
so `duckdb_result` and `duckdb_result_arrow` each carry an `env` slot,
an environment holding the fetch counters and the open/completed flags,
which survives being passed by value.

`duckdb_connection` also carries `timezone_out`, `tz_out_convert`,
and `bigint`,
which are marked deprecated:
they are superseded by the `convert_opts` list,
copied from it at construction,
and no longer read internally.
They stay for back-compatibility with code that reaches into the slots.

Three names do double duty as class and constructor
(`duckdb_connection`, `duckdb_result`, `duckdb_result_arrow`);
the constructors are internal, and `dbConnect()` is the public route in.

Outside S4 there are four S3 classes —
`duckdb_relation`, `duckdb_expr`, `duckdb_storage_status`,
and `duckdb_explain` again,
which is an S4 class extending `data.frame`
but takes an ordinary S3 `print` method rather than a `setMethod()`.
Their methods are registered statically in `NAMESPACE`,
since every generic they extend comes with R itself.

## Deferred S3 registration

The hard dependency set is small:
`DBI` under `Depends`,
`methods` and `utils` under `Imports`, and nothing else.
dbplyr, dplyr, adbcdrivermanager, and rlang are suggested.
A method for a suggested package's generic
cannot be declared in `NAMESPACE`,
because `S3method(dbplyr::dbplyr_edition, duckdb_connection)`
would make dbplyr a hard dependency.

`.onLoad()` in `R/zzz.R` registers those methods instead,
through `s3_register()` in `R/s3_register.R`
(vendored from rlang's compatibility file, and `# nocov`-excluded):
dbplyr generics and `dplyr::tbl` on `duckdb_connection`,
and adbcdrivermanager generics on the ADBC wrapper classes.
The `s3_register()` calls in `.onLoad()` are the list.
`s3_register()` does three things worth knowing:
it installs a `packageEvent(pkg, "onLoad")` hook,
so registration also happens when the other package is loaded later,
or unloaded and loaded again;
it looks the method up afresh on every registration,
so `devtools::load_all()` picks up an edited method;
and when the generic is missing it stays silent,
except under `NOT_CRAN=true`, where it warns.

`.onLoad()` carries the other half of the rlang soft dependency too.
`R/rlang.R` holds base-R fallbacks
for the rlang functions the package uses —
`is_interactive()`, `check_dots_empty0()`, `inform()`, `arg_match()` —
each named to match the original.
When rlang is installed,
`.onLoad()` overwrites them with the real functions
and swaps `rapi_error()` for its rlang-based variant;
when it is not,
it calls the generated `rethrow_restore()`,
so the `rethrow_rapi_*()` wrappers stop routing through
`rlang::try_fetch()` and the package runs without rlang at all.

## Boundaries

`duckdb_register()` and `duckdb_register_arrow()` are two plain
functions, not one generic dispatching on the object being registered
([#98](https://github.com/duckdb/duckdb-r/issues/98)).
The reasoning against changing that:
registering a source the package does not yet understand —
a nanoarrow array, a polars data frame —
requires new C++ glue regardless,
and once the glue is being written
a new `duckdb_register_*()` function costs no more than a method
while keeping each source's arguments and errors its own.
The issue stays open as a possible future fix,
not as a documented shape.

`rel_to_altrep()` still takes `allow_materialization`
([#1052](https://github.com/duckdb/duckdb-r/issues/1052)).
It is an internal relational-API function (`@noRd`),
and the argument is no longer passed to the glue:
`allow_materialization = FALSE` is folded into `n_cells = 0`
before the call.
Removing it is a code change to be coordinated with duckplyr,
which is the caller;
until then the argument is accepted and honoured.

The user-facing surface of everything here
is the reference pages shipped in the tarball —
`?duckdb`, `?duckdb_connection-class`, `?duckdb_register`.
Those are generated from the roxygen in `R/`;
`man/*.Rd` is never edited by hand,
and never links into the handbook,
which `.Rbuildignore` keeps out of the tarball.
