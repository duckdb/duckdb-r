# Warnings

What the compiler is allowed to say about this package,
who answers for each file it says it about,
and where that is checked.
[`scripts/warnings.sh`](/scripts/warnings.sh) is the check;
this page is why it holds the flags it holds.

**A warning belongs to the file it points at,
not to the translation unit that raised it.**
Fifteen glue files include a thousand engine headers,
so most of what a glue compile prints is the engine talking —
and a glue author can do nothing about it,
while the person who can is vendoring, not writing glue.
So the tree is divided into scopes by who can fix a line,
each scope is judged on the files it owns,
and what another scope owns is counted rather than listed.

* **`glue`** — everything under `src/` that is not `src/duckdb/`,
  headers included.
  Fixed here, in a pull request against `main`.
* **`vendored`** — `src/duckdb/`, engine and its third-party trees alike.
  Fixed as a patch under [`patch/`](/patch)
  and sent upstream
  ([`operations/vendoring/pipeline/`](/handbook/operations/vendoring/pipeline/README.md)).
* **`cpp11`** — `inst/include/cpp11/`, and nobody's here:
  the copy comes from the
  [`krlmlr/cpp11`](https://github.com/krlmlr/cpp11) fork
  ([`architecture/glue/conventions/`](/handbook/architecture/glue/conventions/README.md)),
  so its warnings are reported and never enforced.
* **`generated`** — dropped outright rather than counted,
  because there is nothing anyone can do with the report.
  An editable fix does not exist for a file its generator rewrites,
  this repository vendors the outputs and none of the generators,
  and the warning cannot be forwarded either:
  it is about generated text, not about the input that produced it.
  `src/cpp11.cpp` (from `cpp11::cpp_register()`),
  `yyjson.cpp` (upstream's amalgamation),
  and libpg_query's bison and flex output.
  This is a list, not a rule — the files carry no marker to match on —
  so it grows when a generated file starts warning.

`src/rfuns.cpp` is the awkward one.
It is in the `glue` scope, because it is compiled and shipped like glue
and formatted like glue — but it is *generated*, by
[`scripts/vendor-rfuns.sh`](/scripts/vendor-rfuns.sh)
concatenating a `duckdb-rfuns` checkout,
and it has no patch stack to re-apply a fix afterwards
([`architecture/rfuns/`](/handbook/architecture/rfuns/README.md)).
A fix that is not also made in `duckdb-rfuns`
is reverted by the next import, silently.

## The sets

`-Wall -Wextra` is the base for both scopes.
The glue adds what a C++ layer between two runtimes benefits from,
and the vendored tree subtracts what a codebase of that size
cannot be held to.
Every departure is a decision, and every decision has a reason:

* **`-Wredundant-move`, off in both.**
  Returning a local `unique_ptr<Derived>` as `unique_ptr<Base>`
  moves either way — P1825 applies to C++11 onward as a defect report,
  and every compiler an R >= 4.2 package meets implements it —
  so the explicit `std::move()` costs nothing,
  and the engine writes it that way ~630 times.
  Removing it from the glue alone would only make the two disagree
  ([#2607](https://github.com/duckdb/duckdb-r/pull/2607)).
* **`-Wunused-parameter`, off in both.**
  Thousands of hits in the vendored tree, nearly all from engine headers
  instantiated through templates: structural at that size, not a defect,
  and not something a patch stack can hold.
  The glue implements those same engine callbacks,
  so holding it to a rule the engine is not held to
  would only make the two disagree —
  the same reasoning as `-Wredundant-move` above.
* **`-Wcast-function-type`, off for `glue`.**
  R registers native routines through `DL_FUNC`, a cast every
  R package makes; `src/cpp11.cpp` alone makes it 61 times, and that
  file is generated by `cpp11::cpp_register()`.
* **Added for `glue`:** `-Wshadow`, `-Wcast-qual`,
  `-Wnon-virtual-dtor`, `-Woverloaded-virtual`, `-Wsuggest-override`,
  `-Wextra-semi`, `-Wduplicated-cond`, `-Wduplicated-branches`,
  `-Wlogical-op`, `-Wnull-dereference`, `-Wmisleading-indentation`,
  `-Wdouble-promotion`.
  The three about virtuals earn their place on their own:
  the glue subclasses engine types, vendoring moves those signatures,
  and an override that quietly stops overriding is a bug no test
  is likely to name.

**None of this reaches `src/Makevars`.**
CRAN rejects `-Wno-*` in a package's own build flags,
and rejects `#pragma` silencing too
([`architecture/glue/conventions/`](/handbook/architecture/glue/conventions/README.md)
owns that rule and the one standing exception).
These are a gate's flags, applied from outside the package —
which is also why an `-Wno-` here is not a suppression:
it says a category is not enforced, not that a warning is hidden.

The gate is GCC's.
Clang names some of these differently and finds a different set;
running it is welcome, wiring a second flag list into the gate is not,
until someone has read what it says.

## Where it runs

* **Locally**, `make warnings`, or `scripts/warnings.sh glue` for the
  fast half — about a minute, and it needs only the checkout,
  because the vendored headers are committed.
  `scripts/warnings.sh <scope> --all` also lists what other scopes own,
  which is how you read the vendored tree's own warnings
  without waiting for a full build.
* **On every pull request**, the `glue` scope, in the `rcc` smoke test
  ([`operations/ci/per-commit/`](/handbook/operations/ci/per-commit/README.md)).
  The answer is the same in every matrix entry, so it runs in one.
* **On the entry that builds from source**, the `vendored` scope —
  and it compiles nothing extra.
  `scripts/warnings.sh flags vendored` puts the flags on that build,
  `scripts/warnings.sh scan vendored` judges its log:
  reading a build that already takes an hour beats running a second one.

That last split is what keeps newly vendored code honest without
paying for it twice, and it is also the gate's one blind spot:
a build that restores objects from `DUCKDB_R_PREBUILT_ARCHIVE`
recompiles nothing and so raises nothing.
The archive's cache key covers `src/duckdb/**`,
so a tree that changed is always built afresh —
which is the only tree this gate is for.

## When a new warning appears

The scope says who fixes it, and the fix is always at the cause:

* **`glue`** — fix it. That is the whole procedure.
* **`vendored`** — a new patch under `patch/`, numbered next,
  and the same change sent to `duckdb/duckdb`;
  [Patch Stack](/BRANCHES.md#patch-stack) has the stack's rules.
  During a vendoring run this arrives like any other breakage the
  walk surfaces
  ([`operations/vendoring/troubleshooting/`](/handbook/operations/vendoring/troubleshooting/README.md)).
  A warning that is upstream's *style* rather than a defect —
  the shape `-Wredundant-move` turned out to be — is the exception,
  and it is answered by moving the category out of the enforced set
  here, with the reason, not by patching 600 files.
* **`src/rfuns.cpp`** — fix it here *and* in `duckdb-rfuns`.
  Only the second one lasts.
* **`cpp11`** — nothing to do here; it is not enforced.
  A fix belongs to the fork.
* **`generated`** — it will not appear;
  the gate drops these before it reports anything.
  Editing the output is undone by the next regeneration,
  and in the vendored tree by the next vendor run as well,
  so there is no version of this worth acting on.

The one answer that is never available is turning the warning off
for a single site.
